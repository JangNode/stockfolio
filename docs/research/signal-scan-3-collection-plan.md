## 1. 공통 설계 (기존 수집기 `collect-short-credit.ts`·`collect-investor-flow-stock.ts` 구조 재사용)

- **대상 종목 420개**: 기존 수급 수집과 같은 목록(2010~ 월말 PIT 시총 상위 150에 한 번이라도 든 종목, 상장폐지 48개 포함; `INVESTOR_FLOW_TOP_N=150`, 종료 유예 14일). 목록은 가격 스냅샷과 월말 시장 구분표로 같은 코드를 다시 계산하며(Storage 읽기는 월말 목록 0.21 MiB), 수급 정리본의 종목 집합과 일치하는지 수집 전에 대조한다. 종목별 조회 기간 = [max(수집 시작일, 첫 가격일), min(마지막 가격일, 수집 종료일)].
- **한계(스캔 해석에 영향)**: 대상은 "월말 시총 상위 150에 든 적 있는 종목"뿐이므로 스캔의 POOL(시총 상위 100)은 완전하지만 MID는 시총 101~150위로 좁아진다(적격 전체의 MID가 아님). SMALL은 제외(이전 스캔 3회차와 같은 이유: 수집 대상이 PIT 진입 이력 종목뿐이라 미래 정보 편향).
- **호출 방식**: `kisGetForResearch`(공용 통로, `batch` 우선순위) 한 개 워커가 **순차 호출**한다. 종목당 한 번에 한 요청. 응답 대기 포함 호출당 0.38~0.5초(2026-10-19 실측, 30행 응답)로 가정, 100행 응답은 0.5초로 보수적으로 잡았다.
- **시간 상한**: 한 회차 최대 4.75시간(워크플로 상한 5시간 − 마지막 저장 여유), 요청 누적 상한은 회차 합산으로 둔다.
- **운영 KIS 한도와 충돌 방지**:
  1. 호출 금지 시간대 KST 14:00~15:40(운영 14:10 루틴·14:30 장중 판정과 겹치지 않게) — 코드가 시작 시와 매 요청 전에 확인하고 걸리면 즉시 저장 후 중단. 실행은 15:45 KST 이후 또는 밤에 시작한다.
  2. 단일 워커 순차 호출(초당 약 2건 = 프로젝트 배치 버킷 12건/초·전체 15건/초의 약 1/6)이라 운영 호출 몫을 거의 쓰지 않는다. `batch` 우선순위라 사용자 요청이 항상 먼저 나간다.
  3. rate limit 응답(EGW00201 등): 5초 → 15초 → 60초 쉬고 같은 요청 재시도(최대 3회), 3회 연속 실패 또는 10분 안에 5번 이상이면 그 회차 중단. 연속 오류 20건이면 중단.
  4. KIS 토큰은 앱키당 하나라 **한 번에 한 회차만** 실행한다(워크플로 concurrency 그룹, 기존 토큰 행 읽기·잠금 로직 사용). 수집 중에는 다른 연구 KIS 호출을 하지 않는다.
- **이어받기**: Storage 진행 파일 `_progress.json`(종목별 커서·완료 여부·행 수·요청 수)과 연도별 Parquet로 이미 받은 종목·날짜를 건너뛴다. 종목 10개마다 또는 20분마다 체크포인트(진행 파일 + 연도 파일 업로드, 업로드 일시 오류 재시도). 중단 후 같은 워크플로를 다시 실행하면 완료 종목은 건너뛰고 미완 종목은 저장된 커서부터 이어 받는다. 키 `(종목코드, 날짜)`로 병합·중복 제거하므로 같은 구간을 두 번 받아도 안전하다.
- **정리본**: 원본에서 (a) 거래일 달력 밖 날짜 제거, (b) 중복 제거, (c) 값이 전부 0인 종목·주가는 있는데 값이 없는 날의 비율 계산(스캔 선행 조건: 전부 0 종목 > 10% 또는 가격 있는데 값 없는 날 > 5%이면 스캔하지 않고 숫자만 보고), (d) 같은 수집 작업 끝에 정리본을 Storage에 올리고 Actions 캐시에도 저장.
- **중단 조건**: 연속 오류 20건, rate limit 규칙, `TIME LIMIT`류 오류, 요청 누적 상한, 회차 시간 상한, Storage 총량 800 MiB 초과 예상.

## 2. 항목별 수집 계획

가정: 거래일 2011-01-03~2026-10-26 3,885일, 2011~2016 1,500일, 2017~2026 2,385일, 2015~2026 2,940일, 2015~2019 1,225일, 2020~2026 1,715일. 종목당 평균 조회 일수 = 전체 거래일 × 0.801(기존 수급 정리본 1,390,464행 ÷ 420종목 ÷ 4,135일, 중간 상장·폐지 반영). 호출 수 중심값 = 420 × (평균 조회일 ÷ 호출당 행 수 + 0.5), 상한 = 420 × ⌈전체 일수 ÷ 호출당 행 수⌉(모든 종목이 전 기간 존재할 때). 시간 = 호출 수 × 0.5초 × 1.05(재시도·체크포인트).

### 2.1 체결강도 (일별 매수체결량·매도체결량)
- API: `inquire-daily-trade-volume` (FHKST03010800), 종목 코드 + 기간 범위. 응답 날짜별 `total_shnu_qty`·`total_seln_qty` 2개 값. **호출당 최대 100행**(2011년 1년 범위 요청에서 100행 확인), 범위의 최신일부터 거꾸로 오므로 다음 호출은 끝 날짜를 마지막 받은 날 −1일로 옮긴다. 2011-01-03~ 확인, 2010년 시작 가능 여부는 3차 호출 결과(`P4d`, 문서 data-feasibility-2.md 8.1절)에 따른다.
- 값 주의: 단일가 체결이 빠져 두 값의 합이 거래량의 약 78~92%. 수량은 분할 미조정 원 주수.

### 2.3 프로그램매매 시장 단위 (차익·비차익)
- API: `comp-program-trade-daily` (FHPPG04600001), 시장 구분 K(코스피)·Q(코스닥), 기간 범위. **1년 범위에 248행**(제한 없음), 약 38개 필드(차익/비차익/전체 × 위탁/자기 × 매도·매수 × 수량·금액·비중). 2011-01-03~ 확인.
- 호출 수: 시장 2개 × 17년(2010~2026) = **34회**(코스닥은 069500 예측에 쓰지 않으므로 코스피만이면 17회). 소요 약 1분. 정리본 약 0.5~1 MiB(필요한 열 약 12개만 저장).
- 이 항목은 1단계에서 전 구간(2010~2026)을 받는다. 호출이 34회뿐이고, 스캔은 학습 구간 값만 계산하며 확인·보류 구간 행은 저장만 한다(사전등록에 계산 금지를 명시).

## 4. 이어받기·검증·안전 장치

- **파일럿(승인된 회차 시작 직후, 대량 전)**: 각 항목 종목 2개(삼성전자, 폐지 종목 1개)를 끝까지 받아 (a) 날짜 연속성, (b) 값이 전부 0인지, (c) 가격 Parquet의 거래일과 대조, (d) 행당 바이트 실측을 출력한다. 이상이 있으면 본 수집 전에 멈추고 보고한다.
- **진행 보고**: 200건마다 로그(요청 수, 행 수, 종목 번호, rate limit 횟수, 남은 예상 시간). 회차 끝 요약: 완료 종목 수 / 420, 요청 수, 쓴 행, 오류, 쓴 바이트, 읽은 바이트.
- **중복·위반 점검**: (종목, 날짜) 중복 0, 날짜가 조회 기간 밖인 행 0, 값이 음수인 행 수(대차 잔고 등), 체결강도 합이 거래량 초과인 행 수.

## 5. 편향·시차 (수집·정의에 반영)

- 대상 종목은 PIT 시총 상위 150 이력이라 시총 순위 150위 밖 종목은 결측이다(MID 한계). 수집 시점 기준 현재 종목이 아니라 과거 구성원 + 상장폐지를 포함한다.
- 체결강도: 장 종료 후 확정 값이라 신호일 d의 값을 d 종가 이후에 쓰고 체결은 d+1 종가(기존 스캔 규칙). 대차잔고: 결제 시차를 알 수 없어 **신호일 2거래일 전까지의 값만** 사용(신용잔고와 같은 보수 규칙). 프로그램매매 시장 단위: 장 종료 후 확정, 신호일 d의 값을 d 이후에 사용.
- 값 정정: 대차·체결량이 사후 정정되는지 확인할 수단이 없다(이 API는 현재 시점 값을 준다). 한계로 공개.

## 7. Storage 영향 (쓰기와 읽기 구분)

**전제**: Storage에는 상한이 두 가지다. ① 저장 총량 상한(수집기가 쓰는 800 MiB 가드, 현재 `stock-daily-prices` 버킷 126개 객체 **434.67 MiB** — 2026-11-05 `pinv list` run 41985237696) ② **내려받기(읽기) 누적 600 MiB, 11-14까지**. 쓰기(업로드)는 ①에만 영향을 주고 ②는 늘리지 않는다. 읽기(내려받기)는 ②에 포함된다. Actions 캐시 읽기는 Supabase 읽기가 아니다.

### 7.1 쓰기 (업로드, ① 저장 총량)
| 항목 | 1단계 | 전체 |
|---|---|---|
| 체결강도 원본 + 정리본 | 약 7~10 MiB | 약 18~26 MiB |
| 대차 원본 + 정리본 | 약 8~10 MiB | 약 19~26 MiB |
| 프로그램매매 시장 단위 원본 + 정리본 | 약 1~2 MiB | 같음 |
| 진행 파일 | 0.1 MiB 미만 | 0.1 MiB 미만 |
| **합계** | **약 16~22 MiB** | **약 38~54 MiB** |
| 저장 총량 도달치 | 434.67 → 약 451~457 MiB | 약 473~489 MiB (800 MiB 가드 이내) |

### 7.2 읽기 (내려받기, ② 600 MiB 누적, 11-14까지)
- **현재 누적**: 마지막 문서 기록(VGT 사전등록, 2026-10-28)은 시험 전 약 471.4~492.4 MiB. 그 뒤 기록된 읽기: 전략 배분용 PE4 입력 부분집합 15.11 MiB(기록), DS6 포워드 첫 실행 약 14 MiB(승인), 그 외 시험·점검 실행당 월말 시장 목록 0.21 MiB(약 40회 가정 약 8 MiB). **합산 약 509~530 MiB, 남은 여유 약 70~90 MiB**로 본다(원로그 확인이 어려운 항목이 있어 범위로 둔다. 수집 승인 전에 실행 로그 기준으로 재집계해 확정 값을 보고한다).
- 이 계획의 읽기:

| 작업 | 읽기(MiB) | 비고 |
|---|---|---|
| 수집 1단계 정상 완료(재시작 없음) | 0.2 (월말 시장 목록) | 진행 파일은 새로 만들어 읽기 0 |
| 수집 중단 후 재시작 1회당(최악) | 체결강도 최대 5, 대차 최대 5 | 이미 받은 연도 Parquet를 병합하려고 다시 읽음 |
| 정리본 생성 | 0 | 같은 작업 메모리에서 정리본을 만들고 올림(재시작이 있었으면 마지막 회차가 원본 전체를 한 번 읽음, 최대 10) |
| 스캔 1회(체결강도·대차 정리본 + 프로그램매매) | 0 | Actions 캐시에서 읽음(수집 작업이 저장). 월말 시장 목록 0.21 |
| 기존 신호 중복(신용잔고 정리본 2011~2019) | **20.6** | **후보가 나온 경우에만** 별도 단계로 읽음 |
| 2단계 수집(확인·보류) | 0.2 (재시작 시 최대 15) | |
| **1단계 합계** | **약 0.4 (최악 약 20)** | 후보 없음 / 최악 재시작 |
| **1단계 + 신용잔고 중복 포함** | 약 21 (최악 약 41) | |
| **1단계 + 2단계 + 중복** | 약 21~22 (최악 약 57) | |

- 결론: 누적 약 509~530 MiB에 더해 1단계 0.4 MiB(최악 20), 중복 단계까지 포함해도 약 21 MiB(최악 41)이므로 **11-14 이전에 1단계와 스캔은 상한 600 MiB 안에서 가능**하다(최악 재시작 시에도 약 550~571 MiB). 2단계와 신용잔고 중복 읽기는 후보가 있을 때만 필요하고, 합산해도 최악 약 57 MiB(누적 약 566~587 MiB)로 여유가 얇아 11-14 이후로 미루는 것을 권장한다.
- Actions 캐시 보존: 캐시는 7일간 사용하지 않으면 지워진다. 스캔 전에 지워졌으면 정리본을 Storage에서 한 번 읽어 복원한다(체결강도 5 + 대차 5 + 시장 1 ≈ 11 MiB 최악).

## 8. 승인 때 확인할 것

1. 2단계 분할(학습 구간만 먼저)로 진행해도 되는지, 아니면 전 구간을 한 번에 받을지.
2. 체결강도를 2010년부터 받을지(3차 호출에서 2010 조회가 되면) — 사용자 지정은 2011년부터.
3. 일 3,000건 상한 규칙의 적용 여부(적용하면 1단계가 약 2~4.6일).
4. 11-14 이전에 신용잔고 중복 단계(약 20.6 MiB 읽기)를 수행할지.
5. 수집용 워크플로 옵션(`which=coll3`)과 스크립트(`scripts/collect-scan3.ts`)를 만들어도 되는지(수집 실행은 별도 승인).
