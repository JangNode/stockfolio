# 시장 국면 일일 배치 — Parquet 현재 연도 파일 증분 갱신안과 Storage egress 추정

## 배경
일일 국면 배치(`scripts/market-regime.ts`)는 연도 Parquet을 읽기만 한다. 현재 연도 파일은 주간 배치(월 05:00 KST)만 채워서,
화~금에는 직전 거래일 시세가 Parquet에 없어 "Parquet에 시세 없음" 오류가 기록되고 카드가 최대 1주 늦는다.
해결안(a): 일일 워크플로가 계산 직전에 기존 `backfill:stock-daily-prices`(기존 날짜 건너뛰기)로 현재 연도 파일만 증분 갱신한다.

|---|---|---|---|---|---|
| 2025 | 17.59 MiB | 643,220 | 242 | 2,658 | 17.63 MiB |
| 2026 | 13.98 MiB | 506,194 | 191 | 2,650 | 14.00 MiB |

- 디스크 캐시 켠 실행(실제 배치와 같은 조건): 두 해 파일 Storage 다운로드 **0 MiB**(적중 2건, 31.57 MiB 절약).
- 디스크 캐시 끈 실행(최악): 다운로드 **31.57 MiB**(2025 + 2026).
- 하루에 파일이 약 +0.02 MiB 자란다.

## 한 번 실행의 Storage 바이트 (새 행이 생긴 날)
| 구분 | 바이트 | 비고 |
|---|---|---|
| 갱신 단계: 기존 파일 읽기 | 0 (캐시 적중) | 직전 실행이 저장한 Actions 캐시를 복원 |
| 갱신 단계: 현재 연도 파일 업로드(ingress) | 14.0 MiB(올해 말 ≈ 17.6 MiB) | egress 아님 |
| 국면 단계: 방금 올라간 현재 연도 파일 다운로드(egress) | 14.0 MiB(올해 말 ≈ 17.6 MiB) | 업로드로 변경 판별값이 바뀌어 캐시 미적중 |
| 작년 파일 | 0 | 새 행이 없으면 업로드하지 않도록 `backfill-stock-daily-prices.ts` 수정(현재는 매번 재업로드해 판별값이 바뀜) |

## 월 22회 실행 기준 egress 추정 (Supabase 무료 egress 5 GB 가정 — 대시보드에서 플랜 확인 필요)
| 시나리오 | 월 egress | 5 GB 대비 |
|---|---|---|
| 제안안(현재 연도만, 새 행 없으면 업로드 생략) — 올해 현재 크기 | 22 × 14.0 = 308 MiB | 6.5 % |
| 제안안 — 연말 크기 | 22 × 17.6 = 387 MiB | 8.1 % |
| 기존 스크립트 그대로(작년·올해 둘 다 매번 재업로드, 둘 다 다운로드) | 22 × 31.6 = 695 MiB | 14.6 % |
| 참고: Actions 캐시가 통째로 만료돼 17개 연도를 한 번 다시 받는 사건 | 230 MiB (1회) | 4.6 % |

모두 20 % 이내. 이 기능이 더하는 양만 계산했고, 앱·다른 배치의 기존 egress는 포함하지 않았다.

## 부수 영향
- Actions 캐시: 새 행이 있는 날마다 약 202 MB 항목이 새로 저장된다(월 22회 ≈ 4.4 GB, 저장소 한도 10 GB, 7일 미사용 항목은 만료).
- concurrency: 일일 국면·주간 백테스트·국면 백필이 같은 그룹(`stock-price-parquet-refresh`)이라 한 번에 하나만 돈다. GitHub는 그룹에
  대기 실행을 하나만 남기므로 대기 중 새 실행이 들어오면 이전 대기 실행은 취소된다.
- KRX 호출: 기존 날짜는 건너뛰지만 파일에 없는 평일(공휴일 포함)은 매번 시세 API를 다시 호출한다(공휴일당 2회).
