## 2. 모의 관찰 가능성 점검 (구현 금지, 보고만)

"DS4를 매일 계산하려면 무엇이 필요한가"를 기존 코드·워크플로·문서로 조사했다. 구현·워크플로 등록·DB 쓰기·외부 호출은 하지 않았다.

### 2.0 이미 있는 일일 인프라 (main 기준)

- **`market-regime.yml`**: pg_cron이 평일 10:00 KST(UTC 01:00, 전 거래일 종가 기준, 휴장일 건너뜀)에 workflow_dispatch로 실행한다. 이 워크플로가 **현재 연도 가격 Parquet을 KRX Open API(`backfill:stock-daily-prices`, SKIP_EXISTING_DATES)로 직전 거래일까지 증분 갱신**하고(Actions 캐시 `parquet-v1` 사용), 같은 가격으로 **그날 K200P 구성(코스피 ∩ 20일 평균 거래대금 ≥ 5억 ∩ 제외 규칙 ∩ 시총 상위 200, `membersOnDate`)** 을 계산한다. 가격 Parquet에는 종가·시가총액·거래량·거래대금이 있다.
- **`screening.yml`**(평일 14:30 KST) 마지막 단계가 hot 표 `stock_daily_prices_recent`(Postgres)를 갱신한다(시총 5천억 하한). DS4 연구 harness는 이 표가 아니라 Parquet을 읽는다.
- **분할·병합 조정계수**: `scan-price-adjustment-events`는 수동 워크플로이고 주간 장기 백테스트 워크플로가 배치 직전에 같은 스크립트를 돌린다. DS4 연구는 DB 표 `stock_price_adjustment_events`(applied)를 읽기 전용으로 쓴다(읽은 행 1,016).
- 없는 것: DART 공시 증분 수집 일일 배치, 외국인 순매수 일일 수집, LightGBM 일일/연간 파이프라인, 월말 시장 구분 목록 정기 갱신(`collect-market-membership.ts`는 수동 일회성, 기간 상수 `MM_TO_MONTH = "2026-10"`), 069500 일별 갱신(DB `etf_daily_prices`는 2026-10-16까지, 연구 보조 파일은 2026-10-26까지).

### 2.2 세부 답변

- **PE4가 영업이익 공시 파싱을 매일 해야 하는가**: 이벤트는 정기보고서 제출 시즌(사업보고서 3/31, 분기 5/15·8/14·11/14 기한)에 몰린다. 연구 사전등록은 "보고서 기한 20일 전 ~ 10일 후"를 공시 시즌으로 보고한다. 비시즌에는 신규 접수가 거의 없으므로 **시즌 중 매일, 비시즌 주 1회**면 충분하다. 파싱이 아니라 DART 주요계정 API 응답(구조화된 값)을 받는 방식이다.
- **PE4 지연**: 연구 정의가 접수일 다음 거래일 종가에 신호, 그다음 거래일 종가에 체결(공시 시각을 모르므로 항상 하루 더 늦춤)이라 이벤트에 필요한 데이터 지연은 **접수 후 하루 이내**면 된다. 접수 당일 저녁이나 다음 날 아침 배치로 수집하면 신호일 종가 전에 확정된다. 다만 2026-10-26까지의 연구에서 DART 접수 시각·정정 처리의 실제 지연은 측정하지 않았다(측정 필요). 정정공시(정기공시의 약 22.5%)는 이벤트로 세지 않는다.
- **W3 재학습 빈도·비용**: **연 1회**(매년 첫 거래일, 학습 행은 예측 연도 직전 H+1 = 6거래일을 제외하는 퍼지 적용). 지금 필요한 일은 ① 2026년 모델 재현(저장된 점수와 일치 확인) 한 번, ② 2027-01 첫 거래일 재학습이다. 정확한 학습 시간은 이번에 측정하지 않았다(연구 WFR 로그에서 확인 가능, 추정: 연 1회 한 모델이 수 분 단위). **일일 점수 계산 비용은 작다**(K200P 약 200종목 × 25특성 × 300트리 추론). 실제 비용은 특성 계산(가격 Parquet 로딩과 롤링 계산, 연구 harness 로딩에 약 1분)과 수급 수집이다.
- **LV1에 필요한 데이터**: 가격(수정 종가·거래대금·시총)만이다. 수급·공시 불필요.

### 2.3 DB 쓰기 없이 가능한가

**가능하다.** 입력은 모두 Storage Parquet(가격 현재 연도 파일, `fin.parquet`·`filings.parquet`, 수급 정리본, 월말 시장 구분)과 DB 읽기 전용(조정계수 이벤트, KOSPI 지수, `dart_corp_codes`)이고, 출력(코어 상태·구성요소별 일별 수익·DS4 가상 일수익률)은 KB~수십 KB의 CSV/JSON 파일 로그로 충분하다. 보관 위치는 ① 연구 브랜치에 결과 파일 커밋(기존에 워크플로가 결과 브랜치에 커밋하는 패턴이 있음) 또는 ② Storage 소형 객체(연구용 경로, 수십 KB). Actions 캐시(7일 미접근 시 삭제)·아티팩트(보존 기간 제한)는 영구 로그로 부적합하다. **Storage 누적 600 MiB 상한**에는 읽기 총량이 문제이므로 `parquet-v1` Actions 캐시를 쓰는 기존 방식을 그대로 따라 Storage 재다운로드를 피해야 한다(`market-regime.yml`은 이미 이 캐시를 쓴다).

### 2.4 가장 가벼운 방식 제안 (만들지는 않음)

**"재생(replay) 방식, 월 1회(필요 시 수동)"**: 고정판 스크립트(`research-ds4.ts`, 정의 그대로)를 확장된 입력으로 다시 돌려 2026-10-27 이후 일별 가상 수익률만 잘라 파일 로그에 쌓는다.

- 상태 저장이 필요 없다(모든 구성요소가 결정적이므로 처음부터 재생). 일일 실행도 필요 없다(가상 수익률은 사후에 일괄 계산 가능). 재생 때마다 설계 구간 값(15.20 / 33.11 등)이 그대로인지 먼저 확인해 정의가 변하지 않았음을 증명한다.
- 입력 확장 최소 목록: ① 현재 연도 가격 Parquet(이미 매일 갱신됨), ② 월말 시장 구분 목록 연장(월 1회 KRX 2요청), ③ 분할 조정계수(주간 스캔 결과, DB 읽기), ④ 069500 보조 파일 연장(KRX 소량), ⑤ **PE4: 신규 정기보고서 증분 수집(시즌 중)**, ⑥ **W3: 외국인 순매수 증분 수집 + 모델 재현 학습 1회 + 2027-01 재학습**.
- 단계적 진행안(구현은 별도 승인 후): **1단계 코어 + LV1 + 069500**(가격만; 새 수집기 불필요, 작은 작업) → 2단계 PE4 증분 수집(중간) → 3단계 W3 수급 수집과 모델(큼). 단, **1단계만으로는 DS4가 아니다**(위성에 PE4·W3가 빠지면 정의가 다르다). 부분 계열은 DS4 가상 수익률이라고 부르지 않고, 3단계가 끝난 뒤에야 DS4 전향 관찰로 쌓는다. 단계 중간 산출물은 구성요소별 일별 수익 로그(코어, LV1, PE4, W3)로 따로 보관하면 나중에 합성만 하면 된다.
- 가장 큰 불확실성: ① W3 외국인 순매수 일별 수집이 KIS 호출 한도·시간 제한(14:00~15:40 KST 금지)·정리 규칙(결측 처리 2/3 규칙)과 연구 정리본의 일치를 유지할 수 있는지, ② LightGBM 재현성(같은 버전·시드), ③ 1.4절의 10-16~10-26 수급 결측 여부.
