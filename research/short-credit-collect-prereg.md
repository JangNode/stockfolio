# 공매도·신용잔고 수집 (학습 구간만, 시도 아님) — 사전 기록

승인 범위: 수집만(백테스트·스캔 금지). 브랜치 claude/ma-v3-portfolio-cap-run (병합 금지). DB 표 생성·쓰기 금지, 저장은 Storage Parquet만. 키 값 출력 금지, psql 금지. 다음 라운드 자동 시작 금지. 누적 시도 횟수(132)는 변하지 않는다.

## 사용자 문안 (원문 요약, 항목 번호는 원문 그대로)
1. 대상: 2010-01~데이터 끝 중 한 번이라도 PIT 유니버스(시총 5천억 + 유동성)에 들어간 종목 1,224개(상장폐지 포함). 기간 2009-10-01~2016-12-31만(그 밖 날짜는 요청·저장하지 않는다).
2. 공매도: KIS FHPST04830000(1회 최대 100행). research/short_sale/연도.parquet, 컬럼 stock_code, trade_date, ssts_cntg_qty, ssts_tr_pbmn, stnd_vol_smtn, stnd_tr_pbmn_smtn만.
3. 신용잔고: KIS FHPST04760000(1회 30행). research/credit_balance/연도.parquet, 컬럼 stock_code, deal_date, stlm_date, whol_loan_rmnd_stcn, whol_loan_rmnd_amt, whol_loan_rmnd_rate, whol_stln_rmnd_stcn만.
4. 순서: 공매도 전 종목 → 신용잔고, 종목코드 오름차순.
5. 실행 규칙: 워크플로 1회 최대 5시간, 이어받기(받은 종목·날짜 건너뜀, 진행 상태는 Storage 진행 파일). 14:00~14:30 KST 호출 금지. 연속 오류 20건·rate limit·TIME LIMIT 발생 시 그 회차 멈추고 보고. 외부 요청 누적 상한 110,000건. Storage 총량이 800MB를 넘을 것 같으면 멈추고 보고.
6. 정리: 주가 Parquet 거래일과 대조해 상장 전·폐지 후·거래정지 행은 정리본(research/short_sale_clean/, research/credit_balance_clean/)에서 제외, 원본 유지. 신용잔고는 deal_date 기준.
7. 보고: 종목 수·요청·저장 행·오류, 누적 진행률, 정리본 파일별 크기·행 수, 주가 있는데 데이터 없는 날의 분포, 값이 전부 0인 종목 수, 연도별 공매도 0인 날 비율, Storage 총량, DB 크기 변화(research_storage_report()).

## 구현 해석 (수집 전에 고정 — 사용자 문안에 없는 부분)
1. **대상 1,224종목**: 중형주 N1~N3 스크립트(8cc8305)와 같은 규칙 — 2010-01-01 이후 어느 날이든 직전 행 시총 ≥ 5,000억 그리고 당일 20일 평균 거래대금(수정주가 기준) ≥ 5억이었던 적이 있는 종목(상장폐지 포함). 실행 때 종목 수를 출력해 1,224와 대조한다.
2. **조회 구간(종목별)**: 시작 = 가격 Parquet의 첫 거래일이 2010-01-04보다 늦으면 그 날(상장 이후만), 아니면 2009-10-01. 끝 = min(2016-12-31, 가격 Parquet의 마지막 거래일). 시작이 끝보다 늦은 종목(기간과 주가 구간이 겹치지 않음)은 요청하지 않는다(진행 파일에 skipped로 기록).
3. **공매도 페이지 넘김**: 파라미터 FID_INPUT_DATE_1 = 종목 조회 시작일, FID_INPUT_DATE_2 = 조회 종료일. 응답(output2)은 최신일 먼저 최대 100행. 100행이 오면 받은 가장 이른 거래일 − 1일을 다음 조회 종료일로 하고, 100행 미만이거나 가장 이른 거래일 ≤ 시작일이면 종목 완료. 응답 행 중 [시작일, 조회 종료일] 밖 날짜는 저장하지 않는다(건수 보고).
4. **신용잔고 페이지 넘김**: 파라미터 FID_INPUT_DATE_1 = 기준 결제일(조사에서 관측: 응답 output 최대 30행, 결제일 기준 최신 먼저, 행마다 deal_date(매매일)·stlm_date(결제일)). 첫 기준 결제일 = min(2016-12-31, 종목 조회 끝 + 5일). 30행이 오면 받은 가장 이른 결제일 − 1일을 다음 기준 결제일로 하고, 30행 미만이거나 가장 이른 deal_date ≤ 시작일이거나 다음 기준 결제일 < 2009-10-01이면 종목 완료. 저장은 deal_date가 [2009-10-01, 2016-12-31]인 행만. 결제일 비단조(한 쪽 안에서 결제일이 내림차순이 아닌 쌍)가 있으면 건수를 보고한다.
5. **기간 규칙의 결과(미리 공개)**: 요청 날짜를 2016-12-31 이후로 보내지 않으므로, 신용잔고는 결제일이 2017년으로 넘어가는 2016년 마지막 매매일(2016-12-29·12-30)이 수집되지 않는다(매매일 + 2영업일 = 결제일). 공매도는 해당 없음. 기간 시작(2009-10-01) 쪽은 요청 기준 결제일이 2009-10-01 이상인 쪽까지만 보내며, 마지막 쪽이 기간 앞(2009-10-01 이전) 매매일 행을 함께 돌려줄 수 있으나 저장하지 않는다.
6. **stnd_vol_smtn·stnd_tr_pbmn_smtn 주의(미리 공개)**: 조사 응답에서 이 두 열은 일별 값이 아니라 조회 구간 시작일부터의 누적 성격으로 보인다(005930 2010-01-04 행: acml_vol 11,963,550인데 stnd_vol_smtn 239,271; 2010-02-03 행: stnd_vol_smtn 8,795,101). 구간·페이지 경계에 따라 값이 달라질 수 있다. 요청대로 저장하되 해석은 하지 않는다.
7. **진행·저장**: 완료 종목 10개 또는 20분마다 연도 파일(공매도 research/short_sale/{2009..2016}.parquet, 신용잔고 research/credit_balance/{2009..2016}.parquet)과 진행 파일(각 경로의 _progress.json)을 저장. 키 = 종목+날짜(공매도 trade_date, 신용잔고 deal_date)로 중복 제거. 연속 오류 20건, EGW00201/rate limit/429, "time limit" 문구, rate limit 재시도 발생 → 즉시 중단. 요청 상한은 공매도+신용잔고 누적 합. 회차 상한 4.75시간(마지막 저장 여유 15분).
8. **Storage 800MB 점검**: 회차 시작과 저장 시점마다 모든 버킷의 총량을 구하고, 총량 + (남은 수집 행 + 정리본 사본 행) × 행당 바이트가 800 MiB를 넘으면 중단. 행당 바이트는 실측 전 25 B 가정, 실측 후 직전 업로드 파일 크기 ÷ 행 수. 남은 행은 대상 종목의 기간 내 주가 행 수 기준 상한이다.
9. **정리본(수집 완료 후 별도 스크립트)**: 주가 Parquet 종목별 거래일(종가 > 0)과 대조해 첫 주가일 이전(상장 전), 마지막 주가일 이후(폐지 후), 사이에 주가 없는 날(거래정지 등)의 행을 제외해 research/short_sale_clean/·research/credit_balance_clean/에 저장(공매도는 trade_date, 신용잔고는 deal_date 기준). 원본은 그대로.
10. 상수는 lib/shortCreditCollectConfig.ts(및 lib/investorFlowConfig.ts)에 둔다.

## 변경 기록 (2026-10-20, 2회차 rate limit 중단 뒤 사용자 지시 — 3회차부터 적용)
1. 호출 금지 시간대 14:00~14:30 KST → 14:00~15:40 KST(UTC 05:00~06:40). 회차는 15:40 KST 이후에 시작한다.
2. rate limit 처리: KIS 클라이언트의 내부 재시도를 끄고(lib/kis.ts `kisGetForResearch`의 선택 인자, 기본값은 기존 동작 그대로), 응답이 rate limit(EGW00201·초당·429)이면 5초 → 15초 → 60초 쉬고 같은 요청을 재시도(최대 3회). 3회 재시도가 모두 실패하거나, 최근 10분 안에 rate limit 응답이 5번 이상이면 그 회차를 멈추고 보고. 재시도 횟수와 대기 시간 합계는 회차 보고에 포함. 재시도한 HTTP 시도도 요청 수에 센다. rate limit은 "연속 오류 20건" 카운터에 넣지 않는다.
3. 유지: 요청 누적 상한 110,000, 회차당 최대 4.75시간, 연속 오류 20건·TIME LIMIT 중단, Storage 800MB 점검. 중단 사유가 없는 회차 종료(시간 상한 등)는 따로 승인을 기다리지 않고 같은 규칙으로 다음 회차를 이어받는다. 신용잔고를 다 받으면 정리본 생성과 최종 보고까지 진행한다.
